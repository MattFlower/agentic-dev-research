## Findings

### A. The comprehension gap — #2 and #1

- **Paper.** Julian Oertel, Jil Klünder, and Regina Hebig, "The Comprehension Gap in LLM-Assisted
  Software Development: An Experiment."
  [arXiv 2611.24216](https://arxiv.org/abs/2611.24216). Published 2026-11-18T10:55:37Z. Oertel and
  Hebig are at the University of Rostock. Klünder is at the University of Applied Sciences |
  FHDW Hannover.
- **Design.** Crossover experiment plus interviews. 35 participants finished (students, academic
  personnel, software developers). Each person meets three Java tasks in three modes: self (no
  LLM), llm (a chat), and unseen (pre-written code, description only). The chat is a locally
  hosted Q8_0-quantized Qwen3-32B, thinking disabled. Comprehension is finding mutations the
  experimenter injected into the participant's own code, or into the unseen solution. Four
  mutations for self and llm, five for unseen. No syntax-error operators. The code compiles. The
  errors are semantic or runtime.
- **Results.** The abstract: 36% report a better understanding of self-written code than of their
  generated code. On average they solved the comprehension task 20% faster for self-written code
  than for generated code and found 11% more mutations. Time until submit was 2 min 3 s self,
  2 min 33 s llm, and 4 min 8 s unseen. The 20% is that pair, not the raw seconds per mutation.
  Programming time was significantly lower with the LLM (14 min 31 s with it, 24 min 41 s without;
  the model says time without it rose 91.3%, p<0.001). High reliance on the chat and low task
  engagement went with significantly decreased comprehension. Raw share found: 88.5% self, 80% llm,
  66.9% unseen. Raw seconds per mutation: 37.1 self, 60.4 llm, 108.5 unseen. The model's marginal
  means are 32.5 s, 41.6 s, and 87.2 s, with a 21.7% reduction for self versus llm (p=0.043). The self-reported solution-comprehension rating predicted `seconds_per_mutation`
  (p=0.041). A one-step increase reduced it by 19.6%. On these tasks, 18 of 33 gave self and llm
  the same rating. In the interviews, all 33 said that in general they do not understand generated
  code as they understand self-written code. The authors write that the mutation task may measure
  recall, and that five mutations versus four may make the per-mutation rate unfair.
- **Evidence:** a crossover experiment. Participants were not in separate groups, so this result
  is not tagged `measured-RCT`. Mixed sample, small Java tasks, a chat rather than an agent.
- **Use.** #2. The backlog already pairs this item with a canary-defect protocol from the earlier
  report. This paper is outside evidence that planted-defect finding, time per mutation and share
  found, separates self-written code, chat-generated code, and unseen code. **Our own idea** for
  the test: on one accelerate PR, plant 3-4 semantic mutations in the agent-written hunks after
  the HR page is read, and log seconds-per-mutation and share found, with vs. without the HR page.
  The paper did not test an agent or that page. #1. The reliance and engagement result supports
  active questioning over a passive summary. Less generated code in the solution, and prompts the
  person wrote rather than copied, predicted faster mutation finding.

### B. Semantic code outlines in XR — #11 and #9

- **Paper.** Ilya Zakharov, Alexey Markin, Konstantin Ostroukhov, Alexey Perminov, Roham
  Koohestani, Ekaterina Koshchenko, and Agnia Sergeyuk (JetBrains Research, Belgrade and
  Amsterdam), "Exploring multimodal AI–XR interactions for software development: From expert
  perspectives to semantic code outlines."
  [arXiv 2611.24334](https://arxiv.org/abs/2611.24334). Published 2026-11-18T12:36:29Z. The arXiv
  comment says submitted to HIMAS 2027, co-located with ACM IUI 2027.
- **What.** Study 1: 13 expert interviews. Study 2: two XR prototypes with 12 professional
  developers. Four tried code that faded to become invisible after it was looked at. Eight tried
  a version that replaced viewed code sections with short descriptions of their purpose. Head
  direction helped determine when to offer the change. Manual input applied it and reopened the
  original code. A demo with seven software-engineering researchers. Headset: PICO 4 Ultra.
- **What they asked for.** Accounts suggested the descriptions gave an overview of unfamiliar code
  and served as reminders on revisit. Comparing a description with the source was hard, and the
  abstract also names headset limits and controls that depart from a normal IDE. Stated
  requirements: make summaries easy to recognize and access, preserve straightforward inspection
  of the original code, and retain familiar navigation and editing.
- **Evidence:** exploratory qualitative. Small sample. An XR headset. Not tagged `measured-RCT`.
- **Use.** A minor note only. #11: one click from a summary back to the code, which this prototype
  did by reopening the source. #9: two depths, a short description and the code, both easy to
  reach. No design change beyond that pointer. It does not move either item.

### C. Qodo Agent Session Review — #5, #8, and #16

- **What.** Agent Session Review (Research Preview), in the same 18 November 2026 post as Auto
  Approval Workflows (Beta). Nastasha Casale.
  [blog](https://www.qodo.ai/blog/introducing-auto-approval-workflows-and-agent-session-review/).
  The brief places the launch in Qodo v3.3. The article text does not say that.
- **Work package.** The `/qodo-agent-session-review` skill in Qodo's Agentic Toolbox gathers every
  PR the agent created in a session, across repositories, plus the decisions and actions behind
  them, packages that into a work package, and opens the assessment on the builder's machine.
  The package covers deviations from the plan (implementation choices and assumptions, where the
  build departed from the plan or added work nobody asked for); a guided path through the code
  (how the PRs fit together, their merge order, and where changes interact; a reading plan shows
  what needs close attention, what can be skimmed, and why); and risks grounded in evidence (a
  verdict, each risk tied to the affected parts and the evidence, with gaps and unresolved
  questions left explicit). Engineers can review the agent's decisions one by one and follow data
  across services one contract at a time. The video line: merge status, risk assessment, the
  contracts a change touches, and a code map of what to read.
- **Example.** The plan said to re-run review when the code changes. The implementation also
  triggers a full re-review when a settings value changes. Every check passes, yet the behavior
  differs from what was intended, and no single diff points to it.
- **X.** [@QodoAI](https://x.com/QodoAI/status/2123054786971152475). Counts supplied for this
  sweep, not re-counted: 13 likes, 2 bookmarks, 2 reposts, 4 replies, 632 impressions. Low. The
  large X engagement on this launch is the partnered auto-approval article, in the hand-off.
- **Evidence:** `vendor`. No outcome data.
- **Use.** #5. A "deviation from the plan" list is a sharper version of decisions: compare the
  session's plan to what was built, and list unrequested work. **Our own idea** for the test: on
  one limitless run that produced 2+ PRs, have HR emit a plan-vs-build deviation list from the
  session transcript and count how many entries Matt confirms as real deviations. #8. A reading
  plan with read-closely versus skim, and why. #16. One page for a whole multi-PR agent session,
  with merge order and where the PRs interact. The approval half of the launch is not a backlog
  item. It is in the hand-off.

### D. Cognitive debt, grey literature — #1, #12, and #5

- **Paper.** Theocharis Tavantzis, Bianca Trinkenreich, Michaela Greiler, Júlia Condé Araújo,
  Marina Condé Araújo, Italo Santos, Alexander Serebrenik, Margaret-Anne Storey, and Maria Teresa
  Baldassarre, "Cognitive Debt in the GenAI Era - Listening to Practitioners' Voices on the Loss
  of Understanding."
  [arXiv 2610.37888](https://arxiv.org/abs/2610.37888). Published 2026-10-27T19:27:21Z. The
  comment says 12 pages, 3 figures, manuscript under review at ICSE-SEIP. Outside this window.
  Not cited in these notes before this pass.
- **What.** A grey-literature review of 76 sources. Practices proposed: documenting design
  rationale, review-sized changes, comprehension gates, knowledge-sharing rituals, and signals
  such as reliability metrics. "Comprehension Gate practices require developers to demonstrate
  understanding of AI-generated code before accepting or merging it." Under AI-assisted
  understanding, practitioners suggest using LLMs to explain unfamiliar code and decisions,
  generate video walkthroughs (GR3), or quiz developers (GR10). GR10 is also described as a quiz
  that prevents the commit until the developer can explain the code. The recommendation to team
  leads: incorporate comprehension gates, for example PR-size thresholds so a change stays
  reviewable, and decision documents for non-trivial AI changes.
- **Evidence:** grey-literature review of practitioner sources. `practitioner`.
- **Use.** Short notes. #1: the quiz as a comprehension gate. #12: review-sized changes and a
  PR-size threshold. #5: decision documents. No new row.
