## Findings

### A. Garden proof-carrying review — #19, #11, #18, #8, and #5

- **What.** [Proof-carrying review](https://docs.gardenscm.ai/concepts/walkthroughs/). Schema:
  [garden pr explain](https://docs.gardenscm.ai/reference/walkthrough/). No date on either page.
  `garden pr explain` has the author write a walkthrough. "This is deliberately not a session
  dump. Raw sessions are enormous, ephemeral, and often personal. A walkthrough is the small,
  curated artifact the author chooses to stand behind."
- **Tree.** "A block's claim is established by its own proof plus the claims of its children."
  "The top-level blocks are the roots; together they prove the PR as a whole." "Sibling order
  is the reading order — it is never re-sorted." `layout` flattens the tree: `top-down`
  (default, "each claim before its sub-proofs"), `bottom-up`, or `sandwich`.
- **Two axes.** "Every block carries both, because "important to understand" and "dangerous if
  wrong" are not the same property." `attention` is `skim`, `review`, or `scrutinize` ("How
  hard to look"). `risk` is `low`, `medium`, or `high` ("Blast radius if it's wrong"). The
  reference says they "are separate axes." "A subtle-but-reversible block and an
  obvious-but-irreversible one need different handling from a reviewer, and collapsing them
  into one "importance" score loses exactly the distinction that routes attention well."
- **Top of the PR.** `confidence` and `critical_path`: "the author's own certainty, and the two
  or three blocks to read if you only have five minutes." The schema comment on
  `critical_path` is "5 minutes? read these". `confidence` is `low`, `medium`, or `high`.
- **Unproven.** The concepts heading is "`unproven` is the most valuable field". "Each block
  lists what the author did not verify. An honest gap list beats any amount of prose". The
  reference says "`unproven` is the highest-value field" and budgets "bullets only, 2 maximum,
  ≤ 15 words each." "A blank `unproven` is honest; a padded one trains reviewers to skip the
  field."
- **Proof.** "Each proof entry is exactly one kind": `test` ("a test that exercises it; CI
  runs it"), `command`, `attachment`, `pointer` ("any code, in the diff or not"), `external`,
  or `note` ("the weakest; pair with unproven"). "Garden does not verify proofs". "To say a
  block is proven by another block, make it a child — that's the tree."
- **Coverage.** The author does not have to cover every hunk. "garden computes the hunks no
  block covers and shows them as an "unaccounted for" list." "An uncovered hunk is a signal
  that the author judged it didn't need explaining".
- **Across pushes.** "marking a block reviewed does not record "I read block b3". It records
  "I have seen these hunks", keyed by a content hash of the covered lines". At the next
  revision a block is reviewed, partial, or unreviewed from that. "It lives in garden's
  backend, with no source-control footprint, and is frozen when the PR merges: a permanent
  record of why this was done and what was verified".
- **X.** The brief's search for gardenscm.ai / "garden pr explain" returned 0 posts. This
  session did not re-count. See Method.
- **Evidence:** `vendor`. No outcome data.
- **Use.** #19, new. The two axes, the five-minute path, and the per-section unproven list are
  not in human-review and not in #1–#18. See the item for what the skill already does.
  #11. A claim established by its own proof plus its children, and a proof entry that is
  exactly one kind, with a pointer at code in the diff or not. Garden does not check the
  proof. #18. The unaccounted-for hunks are the author's choice not to explain a hunk, shown
  so a reviewer can ask why. #8. Sibling order is an author-chosen reading order, and the
  tool does not re-sort it. That job is the shipped `focus` and `concerns`. The page does not
  describe a semantic diff or a call-graph order, so #8's body stays as it is. Leaving out
  imports, renames, formatting, and generated code is the shipped mechanical tier, with the
  uncovered hunks listed under #18. #5. The walkthrough is the curated why, explicitly not a
  session dump, and it is frozen at merge as "why this was done and what was verified".
  #17. Reviewed state follows a content hash of the hunks, so a re-blocked walkthrough does
  not make the reader re-read lines they have seen. Open PR #33 already has Qodo's
  read-closely versus skim on #8. That is one axis. It is not copied here.

### B. Proofline Walkthrough — #6, #17, #18, and #11

- **Post.** The Proofline team, 10 November 2026.
  [Week of November 9, 2026](https://proofline.sh/blog/faster-reviews-and-walkthroughs/).
  The HTML time element is `datetime="2026-11-10"`. Outside this window. Not cited in these
  notes before this pass.
- **Walkthrough.** "The new Walkthrough explains a change in reading order, with cited code
  beside each step. Starting with the pull request's purpose, it connects that purpose to
  what the diff does. When Author check appears, it highlights behavior omitted from the
  description or claims unsupported by the implementation." "Any illustrations are labeled
  as illustrations and are not checked against the code."
- **Ask.** "Each step gives you a place to investigate further: choose Ask about this, or
  select specific lines and choose Ask about lines. Answers can include the code they cite".
  "When a step's answer cites code and leaves nothing unsettled, it becomes part of the
  walkthrough under Answered questions for other organization members. After a later push,
  the answer stays under steps whose code did not change, while Changed markers identify
  rewritten steps. The earlier walkthrough remains available for comparison."

  ties them to parallel investigations, reused source reads, and less wait before publishing
  findings. That is review runtime. It is not a comprehension result, and it is not attached
  to a ranked item.
- **Across repositories.** "walkthrough steps can show consumers in related repositories,
  helping readers follow a change across repository boundaries." Related repositories must
  belong to the same organization and GitHub installation. A finding names one only when
  every reader of the pull request can read it.
- **Evidence:** `vendor`. No outcome data for the walkthrough.
- **Use.** #6. Ask about this, and Ask about lines. An answer that cites code and leaves
  nothing unsettled is saved on the walkthrough for other organization members. #6 already
  adds an answer to the page as a note. The org-wide save, and the "leaves nothing
  unsettled" bar, are the detail. #17. After a later push the answer stays under unchanged

### D. AR Labs, four tools — #5, #1, #3, and #7

- **Page.** [Understanding code that AI coding agents write](https://arlabs.tech/engineering/understanding-agent-written-code).
  The HTML aside's Rev is 2026-11-13. That is the date the page shows. It is a Rev, not a
  labeled publication date. Outside this window. Not cited here before this pass.
- **During the build.** "Every implementing agent writes a walkthrough as it works, one
  entry per step, recording what changed and why, in the order it happened. It is written
  while the reasoning is still in the agent's context, because a walkthrough reconstructed
  afterwards from the diff loses the why." "Walkthroughs are written on every implemented
  task in our coding pipeline."
- **After a change.** Comprehend "writes a reading guide in a fixed order: a plain-English
  overview, the runtime flow from entry point to outcome, where the change sits in the
  architecture, five to nine reading chunks of the actual code with margin notes, a file
  map, and the invariants that hold it together. If the change altered the system's
  structure, it adds a C4 diagram showing only what moved. It can finish with a short
  self-check quiz. It is run on demand by a person who wants to understand, never as a
  gate." "Flow order, not file order." "Explain, then ask. A question guides thinking only
  once the reader has the context to answer it." The worked example is labeled
  "Illustrative example, with generic names."
- **A codebase.** "The Walkthrough skill produces a linear tour of a codebase in which
  every code excerpt is pulled from the real files by a command, using Simon Willison's
  Showboat tool. Because the excerpts are generated rather than typed, none of them can
  be invented or drift from the source." The page links
  [Showboat and Rodney](https://simonwillison.net/2026/Feb/10/showboat-and-rodney/).
  Showboat is already on #4 and on the shipped table.
- **Before building.** "The Code Tutor method reverses the usual roles. Its first phase
  follows a practice Geoffrey Litt describes in his essay "Code like a surgeon": before a
  big task, an agent works in the background to write a guide to the relevant parts of the
  codebase, so the person starts prepared." The page links the essay
  ([Code like a surgeon](https://www.geoffreylitt.com/2025/10/24/code-like-a-surgeon)).
  This pass did not read the essay. The page's own version: the agent "writes a tutorial
  on the feature to be built: its purpose, current structure, dependents, likely pitfalls
  and a suggested order of work. It edits no code. Then, in a live session, the agent
  tutors and the person writes every line. Help escalates only as needed, from a
  question, to an explanation of the mechanism, to the pattern the codebase uses, and
  only then to syntax." "Comprehend is in use on changes from that pipeline, Walkthrough
  is available for codebase orientation, and the two Code Tutor commands are in use as
  Claude Code slash commands."
- **Evidence:** `practitioner`. The team's own practice. No outcome data. The example is
  illustrative.
- **Use.** #5. The why is written while the agent still has the context. A reconstruction
  from the diff loses it. #1. An optional self-check quiz, on demand, never a gate. The
  "explain, then ask" rule is the other order from the ask-before-reveal slice already on
  #1. That slice stays. #3. A guide written before the person writes the code, then a live
  tutor while the person writes every line, and a linear codebase tour whose excerpts come
  from a command. Open PR #31's rederive is a derive-the-design session that will not tell
  the design. This is the other shape, and that note is not copied. #7. A C4 diagram of
  only what moved. #8. A pointer only: flow order, and five to nine chunks with margin
  notes. The fixed order is a reading guide. It is not the semantic diff on #8.
