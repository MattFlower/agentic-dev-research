## Findings

### A. rederive — #3 and #1

- **What.** [rederive](https://github.com/EricJujianZou/rederive). Site:
  [ericzou.dev/rederive](https://ericzou.dev/rederive/). MIT skill for Claude Code, Codex, and
  other coding agents. Install: `npx skills add EricJujianZou/rederive`. Repo created 2026-10-19.
  GitHub API on 2026-11-18: `stargazers_count` 1046. The site badge showed 1,025★.
- **How a session goes.** It states the problem a part of the code solves and asks how you would
  build it, then adds constraints one at a time until you reach the design the code uses. It will
  not tell you the design, even when you ask. When you get there it names the pattern. The FAQ's
  example is a middleware chain. A background agent maps the repo while you answer, from the code,
  the import links between files, and the commits where the design changed. The FAQ says it reads
  diffs and does not trust commit messages, so a repo an AI built in a few big commits works too.
  The map holds 5 to 10 problems in the order the system would be built, in `.rederive/map.md`.
  When you are stuck it narrows to a few approaches to pick from. After two wrong answers in a row
  the README offers a sketch. The struggle log is `.rederive/log.md`. `.rederive/` is in the local
  git exclude.
- **X.** Modest. Counts as read from the X API on 2026-11-18 ~13:35 UTC; not re-counted.
  [vintcessun](https://x.com/vintcessun/status/2121869821575078201): 21 likes, 13 bookmarks,
  21 replies.
  [fngly343149](https://x.com/fngly343149/status/2122540806925844634): 4 likes. That post's title
  says 966 stars. The adoption figure here is the API's 1,046.
- **Evidence:** `practitioner` + `engagement` (stars). No outcome data.
- **Use.** #3. A possible derive mode for teach-code: problems in build order,
  constraint-by-constraint hints, and the struggle log as the learner profile. **Our own idea**
  for the test: run `/rederive` and teach-code v1 on the same area of accelerate, then compare how
  well the reader can explain the design a day later. #1. The open-ended, generative counterpart
  to the multiple-choice questions. The reader produces the design. The multiple-choice block
  stays.

### B. Code Bearings — #1

- **Post.** Michael Pellegrin, 4 November 2026.
  [Code Bearings](https://mdpellegrin.com/blog/2026-11-04-code-bearings/). A local browser viewer
  opens a prepared quiz file about a repository or a committed change. Questions are about
  relationships and behavior: where a responsibility belongs, and how data moves. Source excerpts,
  with filenames and original line numbers, stay hidden until the reader reveals the answer. There
  is an "I'm not sure" option. One person can share the browser during a team call.
- **Evidence:** `practitioner`. The author's own report of using it on his applications. The page
  says broader usability and learning effectiveness still need evidence from other people.
- **Use.** #1. Support for reveal-gated source evidence and the "I'm not sure" option.

### C. ship-signal pull request #3 — #11

- **What.** [Pull request #3](https://github.com/SuchintK/ship-signal/pull/3), merged
  2026-11-18T10:49:42Z. It adds `scripts/walkthrough.py` with `snippet`, `refresh`, and `check` for
  offline pull-request walkthrough HTML. Snippets are read from committed git blobs and pinned to
  their source SHA. `refresh` shows a unified diff before an explicit write. It refuses ambiguous
  or changed snippet boundaries unless a deliberate selection with unique anchors resolves them.
  `check` validates exact excerpts, captions, source and base ancestry, links, and anchors. The
  pull request says those checks run in the existing required Rust job, and that one command
  validates 31 source excerpts and 84 links across pull requests #1 and #2. `scripts/walkthrough.py`
  on `main` matches that description.
- **X.** [swarly](https://x.com/smirf_05/status/2123003554109833495): "didn't know this was
  possible until i tried @mattpocockuk's /retro skill." The post's short link redirects to this
  pull request. 2 likes. Counts not re-counted. Weak. The pull request body does not mention the
  skill.
- **Evidence:** `practitioner`, plus weak `engagement`.
- **Use.** #11. A concrete pattern for grounded claims. **Our own idea:** HR's `build --check`
  could verify that every code block matches the blob at its recorded SHA.

### D. GitHub artifacts for the why — #5

- **Paper.** Ziv Nevo, Orna Raz, and Karen Yorav, "Uncovering Code Insights: Leveraging GitHub
  Artifacts for Deeper Code Understanding."
  [arXiv 2511.03549](https://arxiv.org/abs/2511.03549). Abs page: [v1] Wed, 5 Nov 2025 15:31:42 UTC.
  It grounds LLM code explanations in pull request descriptions, issue descriptions and
  discussions, and commit messages. Three components extract and structure that context, generate
  a high-level explanation of the code's purpose, and validate the explanation. Shipped as a
  standalone tool and as an MCP server. A small-scale user study, with developers of open projects
  and of proprietary projects.
- **Evidence:** the paper's user study. Research support. The abstract gives no sample size, so
  none is recorded here.
- **Use.** #5. Draw the "why" from pull request and issue artifacts when there is no agent session.

### E. Hierarchical summarization — notes only, #9 and #3

  Matters: Improving LLM-Based Code Summarization with Hierarchical Information."
  [arXiv 2611.18964](https://arxiv.org/abs/2611.18964). Abs page: [v1] Fri, 13 Nov 2026 21:40:43 UTC.
  The arXiv comment says accepted and presented at the Brazilian Symposium on Software Quality
  (SBQS 2026), Technical Track. An in-silico study. It varies how much of the function, class, and
